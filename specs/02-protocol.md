# 02 — Protocol (v1)

Status: draft v0.3 · Implemented in `packages/core`

Everything in this file is normative. Byte strings are written in hex. `||` is
concatenation. `utf8(x)` is the UTF-8 encoding of string `x`. `u32be(n)` is `n` as 4
big-endian bytes.

## 1. Share string

The share string is the only thing the two humans exchange.

```
pw1_<base32(secret)>[@<relay-host>[:<port>]]
```

- `secret`: 32 bytes from a CSPRNG, generated by the client running `/pairwire:start`.
- `base32`: RFC 4648 alphabet, **lowercase**, no padding → exactly 52 characters. 32 bytes
  is 256 bits and 52 characters carry 260, so the last character's 4 low bits are padding
  and **must be zero**; decoders reject non-canonical strings.
- `@<relay-host>[:<port>]`: present only when the room uses a relay other than the built-in
  default (REQ-INST-2). Hostname is lowercased; IDNs are not supported.
- Regex (after trimming whitespace and lowercasing):
  `^pw1_[a-z2-7]{52}(@([a-z0-9.-]{1,253}|\[::1\])(:[0-9]{1,5})?)?$`
  plus a code check that the port, if present, is 1–65535.
- Parsers accept surrounding whitespace and uppercase base32 and reject anything else with
  a specific error (REQ-ROOM-8). Error messages never echo the input.

Relay URL derivation:

- No host part → built-in default relay (constant `DEFAULT_RELAY_HOST` in
  `packages/core/src/config.ts`, set before first release). While it is unset (`null`),
  a share string without a host part is refused with "no default relay configured; set
  PAIRWIRE_RELAY", and `start` requires a configured relay.
- Host part → `wss://<host>[:<port>]`.
- `ws://` (plaintext) is used **only** when the host is `localhost`, `127.0.0.1` or `[::1]`
  (local development and tests).

## 2. Key schedule

HKDF-SHA256 (RFC 5869) with `salt = utf8("pairwire/v1")` unless stated otherwise.

```
room_id_bytes = HKDF(ikm = secret, salt, info = utf8("room-id"), L = 16)
room_id       = base32(room_id_bytes)                 # 26 lowercase chars, used in URLs
psk           = HKDF(ikm = secret, salt, info = utf8("psk"),   L = 32)
hello_key     = HKDF(ikm = psk,    salt, info = utf8("hello"), L = 32)
```

The relay learns `room_id` only. It cannot derive `psk` from it.

## 3. Transport framing

One WebSocket per client per room: `GET /v1/rooms/<room_id>` upgraded to WebSocket.

- **Text frames** are relay control messages (JSON, section 5). The relay reads them.
- **Binary frames** are end-to-end data. The relay forwards them unchanged (it reads only
  the first byte, to apply the buffering rule for HELLOs).

Binary frame layouts:

```
HELLO: 0x01 || epoch (4, u32be) || e_pub (32) || nonce (24) || ciphertext
MSG:   0x02 || sid (8)          || nonce (24) || ciphertext
```

Maximum binary frame size: 32 KiB (the relay enforces 64 KiB as a hard cap).

## 4. Handshake

The handshake is symmetric: there is no initiator. It runs every time both members are
connected, so each connection pair gets fresh session keys.

### 4.1 Epochs and when to send a HELLO

The relay keeps a per-room counter `epoch`, incremented every time either member's socket
is accepted. It reports the current value in `joined` and `peer_joined` (section 5). A
HELLO is bound to one epoch; this prevents a HELLO meant for an old socket from being
paired with a new one.

A client generates a new ephemeral X25519 key pair `(e_priv, e_pub)` and sends a HELLO for
epoch `E`:

- on receiving `joined` with `peer_present: true` and `epoch: E`, and
- on receiving `peer_joined` with `epoch: E`.

A client keeps handshake state only for the **latest epoch it has seen**. It accepts at
most **one** HELLO per epoch. HELLOs for an older epoch, a second HELLO for the same
epoch, and HELLOs for an epoch the client has not seen yet are dropped and counted. (A
peer can only restart its handshake by reconnecting, which creates a new epoch.)

### 4.2 HELLO contents

```
hello_payload = utf8(JSON)   # schema below
nonce         = 24 random bytes
aad           = utf8("pairwire/v1/hello") || room_id_bytes || u32be(epoch) || e_pub
ciphertext    = XChaCha20-Poly1305(key = hello_key, nonce, aad).seal(hello_payload)
```

```jsonc
{
  "v": 1,
  "name": "Tazo",                 // display name, 1..40 chars after sanitizing; empty → "anonymous"
  "harness": "claude-code",       // "claude-code" | "codex" | "cursor" | "gemini-cli" | "opencode" | "other"
  "client": "pairwire/0.1.0",
  "instance": "k3v9...",          // random 16 bytes, base32; stable for the life of the room locally
  "caps": ["ack", "say"]          // capability flags; unknown flags are ignored
}
```

`harness` is informational (REQ-X-1). A receiver reads any value outside the list as
`"other"` instead of rejecting the HELLO, so a newer client's harness never breaks the
handshake. A HELLO whose decrypted payload fails the schema in any other way (`v` != 1,
missing field, `instance` not 26 base32 characters, invalid JSON) is dropped, but not
counted as a decrypt failure.

A HELLO that fails to decrypt is dropped and counted. After 5 failures on one connection
the client disconnects and tells its human "someone with the wrong key is in this room"
(a local notice, `04-client.md` section 5). It then stops reconnecting to this room until
the human runs a pairwire command, and `status` shows the error.

### 4.3 Session keys

On accepting a peer HELLO for the current epoch (peer ephemeral public key `p_pub`):

```
abort if p_pub == e_pub
dh       = X25519(e_priv, p_pub)            # abort if dh is all zeros
lo, hi   = sort_bytewise(e_pub, p_pub)
okm      = HKDF(ikm = dh, salt = psk, info = utf8("session") || lo || hi, L = 64)
key_lo   = okm[0:32]     # the client whose e_pub == lo SENDS with key_lo
key_hi   = okm[32:64]    # the client whose e_pub == hi SENDS with key_hi
sid      = SHA-256(lo || hi)[0:8]
```

Each client therefore has a **send key** and a **receive key** (the peer's send key) per
session. The session becomes **current** once the client has sent its HELLO and accepted
the peer's. It becomes **confirmed** when the first MSG from the peer under that `sid`
decrypts (in practice the peer's first ack). Reliability does not depend on confirmation
because unacknowledged envelopes are always resent (section 6.2).

### 4.4 Stored sessions

Each client stores its **current** and **previous** session (sid, send key, receive key)
in room state on disk (`04-client.md`, file mode 0600). An incoming MSG is decrypted with
the **receive key** of the session matching its `sid`; a frame with an unknown `sid` is
dropped and counted. Keeping the previous session lets a client read frames the relay
buffered while it was offline, which were encrypted before the newest handshake.

### 4.5 Security properties (and limits)

- Only holders of the share secret can produce a HELLO the peer accepts.
- A passive observer who later learns the share string still cannot decrypt traffic,
  because session keys depend on ephemeral private keys.
- An **active** attacker who has the share string **and** controls the relay can
  impersonate either side. Mitigations: the relay seals rooms (section 5), clients show
  the peer's name and warn when the peer's `instance` changes. Out of scope for v1:
  short authentication strings. Listed as residual risk in `05-security.md`.

## 5. Relay control protocol (text frames)

Client → relay:

| Frame | When |
|---|---|
| `{"t":"join","v":1,"token":null}` | First frame on a new connection, within 10 s. `token` is `null` on first join, or the token the relay issued earlier. |
| `{"t":"leave"}` | User ended the room. The room is over for both members. |
| `{"t":"ping"}` | Keepalive every 30 s, exact bytes. Answered with `{"t":"pong"}` by auto-response, at any time (also before `join`). It is not activity and does not count as the first frame for the join rule. |

Relay → client:

| Frame | Meaning |
|---|---|
| `{"t":"joined","member":"a","token":"<base64url 32 bytes>","epoch":7,"peer_present":false,"buffered":0,"expires_at":1760529600000}` | Join accepted. Store `token` in room state; it is required to rejoin this slot. `expires_at` is the room's max-age deadline (relay creation time + max age, ms since epoch); clients delete the room locally at that time. |
| `{"t":"peer_joined","epoch":8}` | The other member connected (or reconnected). |
| `{"t":"peer_left","reason":"disconnected"}` | The other member's socket closed; their slot is kept. |
| `{"t":"peer_left","reason":"left"}` | The other member sent `leave`. The room is over. Followed by close 4003. |
| `{"t":"error","code":"<code>","retry_after":30}` | Non-fatal error (`rate_limited`, `buffer_full`, `too_large`). The frame that caused it was dropped. `retry_after` in seconds, optional. |

Close codes:

| Code | Name | Meaning | Client retries? |
|---|---|---|---|
| 1000 | normal | Client-initiated close | — |
| 4001 | `room_full` | Both slots are taken and the join has no token (REQ-ROOM-4) | no |
| 4002 | `bad_token` | Token supplied but it matches no slot (whether or not a slot is free). The client treats this like 4003: the room is gone | no |
| 4003 | `ended` | Room ended (`leave`), expired, or past max age (REQ-ROOM-7) | no |
| 4004 | `unsupported_version` | `v` not supported | no |
| 4005 | `protocol_error` | First frame not `join`, or malformed control frame | no |
| 4006 | `join_timeout` | No `join` within 10 s | yes |
| 4007 | `replaced` | Another connection rejoined this slot with the same token | no |
| other | network / server error | | yes, with backoff |

Membership rules:

1. A join with `token: null` takes the first free slot (`a`, then `b`) and receives a new
   token. A room with no free slot refuses it with 4001. Once both slots have been taken,
   the room is **sealed**: knowing the share string is no longer enough to get in.
2. A join with a token matching a slot takes that slot back. Any older socket on that slot
   is closed with 4007. A join with a token that matches no slot is closed with 4002, even
   if a slot is free, so a stale client can never re-create a room the relay has deleted.
3. `leave` ends the room. The relay marks the room **ended** (a tombstone kept until the
   room's max age), discards all tokens and buffered frames, sends `peer_left` with
   `reason: "left"` to the other member if it is connected, and closes both sockets with
   4003. Any later join to an ended room (with or without a token) receives
   `peer_left` (`left`) first if the room ended by `leave`, then close 4003. This needs no
   token and reveals only that the room ended.
4. Ordering on (re)join: the relay sends `joined`, then any buffered binary frames in
   order, then `peer_joined` to the other member.
5. HELLO frames (first byte 0x01) are never buffered; they are dropped if the peer is not
   connected. Binary frames sent while the other slot has never been taken are dropped too:
   compliant clients send no MSG before a session exists (§6.2), which needs both members.
6. Open sockets count as activity: a room with at least one connected member never hits
   idle expiry.

## 6. Envelope (plaintext of a MSG frame)

```
nonce      = 24 random bytes
aad        = utf8("pairwire/v1/msg") || room_id_bytes || sid
ciphertext = XChaCha20-Poly1305(key = my send key for sid, nonce, aad).seal(utf8(JSON envelope))
```

```jsonc
{
  "v": 1,
  "id": "01JABCDEF...",          // ULID, unique per message
  "seq": 17,                      // per sender, per room; starts at 1, +1 per non-ack envelope; always 0 for "ack"
  "ts": "2026-10-15T12:00:00.000Z",
  "author": "agent",              // "agent" | "human"  (human = sent with /pairwire:say)
  "kind": "chat",                 // see table
  "reply_to": null,               // message id, required for "answer"
  "body": "markdown text",        // required for chat/question/answer; max 24 KiB of UTF-8
  "acks": null                    // highest seq received in order, only for "ack" (see 6.2)
}
```

Size limits: the **serialized** envelope (UTF-8 JSON) is at most 28 KiB, so the frame
stays under 32 KiB. This is the binding limit, because JSON escaping can make the
serialized body several times larger than the raw body. `body` is additionally limited to
24 KiB of UTF-8. A sender rejects a message that breaks either limit (error `too_large`,
reporting both sizes); a receiver drops and counts an envelope that breaks either.

| kind | Meaning | Shown to agent? |
|---|---|---|
| `chat` | General message | yes |
| `question` | The sender wants an answer | yes, marked as awaiting an answer |
| `answer` | Reply to a `question`; `reply_to` required | yes |
| `ack` | Delivery receipt (REQ-MSG-6) | no — updates delivery status only |
| `bye` | Sent just before `leave`, optional `body` | yes, as "peer ended the room" |

Reserved for M5 (do not implement before then): `heads_up`, `claim`, `release`,
`contract_propose`, `contract_response`.

### 6.1 Receiver rules

The receiver keeps `peer_max_seq`, the highest seq accepted **in order**.

- Drop and count envelopes that fail schema validation or have `v` != 1. Unknown `kind`
  values are dropped and counted, not shown to the agent.
For non-ack envelopes:

- `seq == peer_max_seq + 1` → accept: append to the inbox and update `peer_max_seq` in one
  atomic state update (`04-client.md` section 3), then schedule an ack.
- `seq <= peer_max_seq` → duplicate: do not deliver again, but schedule an ack (the
  sender evidently missed the earlier one).
- `seq > peer_max_seq + 1` → out of order (an earlier frame was lost): drop without
  acking; the sender's resend fixes the gap.
- An ack is a single `ack` envelope with `seq: 0` and `acks = peer_max_seq`, sent within
  2 s of the triggering frame, batching everything that arrived meanwhile.
- `ack` envelopes sit outside the ordering: they are processed whenever they arrive
  (a higher `acks` value supersedes a lower one), never change `peer_max_seq`, and are
  never acked.

### 6.2 Sender rules (reliable, ordered delivery)

- Assign `seq` and persist the new `my_seq` **before** the frame is written to the socket,
  so a crash can never reuse a seq.
- Keep every non-ack envelope in the outbox until an ack with `acks >= seq` arrives. Mark
  it delivered then (REQ-MSG-6).
- Send under the current session whenever one exists, even if the peer is disconnected
  (the relay buffers, REQ-MSG-5). Before the first session ever exists, envelopes wait in
  the outbox.
- Resend all unacked envelopes, in seq order, with the **same id and seq**, re-encrypted
  under the current session: (a) after each new session becomes current, and (b) when the
  oldest unacked envelope is 15 s old with no ack while the peer is connected.
- Pace binary frames to at most 8 per rolling 10 s, counting HELLOs, acks and resends, so
  a resend burst stays below the relay's limit (`03-relay.md`). On `error rate_limited`,
  wait `retry_after`, then resend unacked envelopes.
- Acks themselves are not kept or resent; the next ack supersedes them.
